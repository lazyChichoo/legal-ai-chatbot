# 面向对美出口卖方的跨境违约救济 AI 预审系统

给中国出口卖方用的法律预审工具。买方拒收、拖欠货款、信用证被拒付……
这类事发生时，卖方最缺的不是律师，而是**在找律师之前先搞清楚自己站在哪儿、手上有哪些牌、
接下来 72 小时该干什么**。本系统就干这件事。

三条硬性设计约束，也是这个项目跟"套壳 ChatGPT"的区别：

1. **法条只能来自知识库。** 回答里出现的每一个法条编号，程序会逐个核对是不是本次
   真的从知识库里检索出来的。编的、记混的、张冠李戴的，一律打回重写。
2. **该说的必须说全。** 某些法律结论少讲一半比不讲更危险（例：买方迟延通知的例外，
   只讲"能减价"不讲"不能索赔利润损失"，卖方会误判自己的风险敞口）。这类"必须讲全"的点
   由程序逐条验收，不指望模型自觉。
3. **不许给出确定性法律意见。** 输出永远是"初步风险提示 + 建议找执业律师"，
   免责声明由程序按提问语言强制贴上，AI 写错了就删掉重贴。

一句话概括这套架构：**AI 负责想，程序负责管。**

---

## 1. 系统由三层组成

```
          用户提问 / 一份合同文本
                   │
   ┌───────────────┼───────────────────────────────┐
   │  第一层：法律知识库与检索                        │
   │  知识导入 → 切块 → 向量化 → Chroma → RAG 召回     │
   │  ingest.py / retrieve.py / chat.py             │
   └───────────────┬───────────────────────────────┘
                   │  相关法律知识 + 风险提示
   ┌───────────────┼───────────────────────────────┐
   │  第二层：AI 问答与管控                           │
   │  必带条文 → 约束 prompt → 调用大模型              │
   │            → 出处校验 / 格式强制 / 硬规则验收      │
   │  kb.py / llm.py / bot.py / *_guard.py          │
   └───────────────┬───────────────────────────────┘
                   │  带出处、带场景、带免责声明的回答
   ┌───────────────┼───────────────────────────────┐
   │  第三层：界面（Streamlit）                       │
   └───────────────────────────────────────────────┘
```

第一层解决"**找得到**"，第二层解决"**说得对、说得全、不许编**"，第三层解决"**用得上**"。
三层可以各自独立跑，也可以拼成完整系统。

### 关于两个 `contract_check`

合并时发现两边各有一个叫 `contract_check.py` 的文件，功能完全不同，
因此把第二层那个改名为 **`contract_prescreen.py`**（合同初筛），第一层保持原名不动。
两者不是重复造轮子，而是互补：

| | `contract_check.py`（第一层） | `contract_prescreen.py`（第二层） |
|---|---|---|
| 回答的问题 | 合同里**写了**什么法律术语 | 合同里**缺**了什么条款 |
| 输出 | JSON 术语命中列表 | 高/中风险报告 + 后果、建议、法律依据 |
| 依赖 | `retrieve.scan_contract` | 无依赖，纯规则 |

## 3. 第一层：法律知识库与检索

这一层负责把法律知识变成机器能检索的形式，并根据用户问题召回最相关的几条。

### 3.1 各文件职责

**`ingest.py`** — 知识导入
- 读取 JSON / JSONL / CSV / DOCX / TXT
- 解析知识字段，校验 `category` 是否属于：实体救济 / 合同审查 / 程序应急
- 逐条切块 → 生成向量 → 写入 Chroma

**`retrieve.py`** — 检索与召回
- 根据用户问题查询 Chroma
- 结合关键词重叠度与向量距离排序
- 返回最相关知识条目、评估考卷命中率、扫描合同关键法律词

**`chat.py`** — 命令行问答
- 接收输入 → 调用 `retrieve()` → 输出相关法律知识（不接大模型）

**`legal_knowledge_20.json`** — 结构化知识源，20 条

### 3.2 知识条目的字段

建议使用结构化 JSON，字段至少包含：

`id` / `title` / `article` / `scenario` / `category` / `keywords` /
`risk_level` / `typical_question` / `answer` / `legal_basis` / `review_points` / `risk_warning`

```json
[
  {
    "id": "demo-011",
    "title": "仲裁条款",
    "article": "仲裁条款应明确仲裁机构或可确定的仲裁机构。",
    "scenario": "审查合同争议解决条款",
    "category": "合同审查",
    "keywords": ["仲裁", "争议解决", "送达"],
    "risk_level": "中风险",
    "typical_question": "合同没有仲裁条款怎么办？",
    "answer": "卖方有权要求仲裁并保留证据。",
    "legal_basis": "CISG Art.61",
    "review_points": "确认仲裁机构和送达方式。",
    "risk_warning": "未约定仲裁可能延误救济。"
  }
]
```

如果用 DOCX / TXT 模板，字段结构应为：

```text
【编号】第11条
【标题】合同没写"买方拒收时卖方可转售"——缺救济条款的风险
【场景标签】合同审查
【风险等级】高风险
【典型问法】合同里只写了买方权利，没写我作为卖家拒收后能干嘛，有什么风险？
【回答】...
【法律依据】...
【合同审查点】...
【关键词】...
【风险提示】...
```

### 3.3 建库与检索

```bash
# 建库（这一步就是 RAG 的建库过程）
python ingest.py --source legal_knowledge_20.json --db ./legal_knowledge_db \
                 --collection legal_knowledge --reset

# 导入整个目录
python ingest.py --source ./knowledge --db ./legal_knowledge_db \
                 --collection legal_knowledge --reset

# 命令行问答
python chat.py --db ./legal_knowledge_db --collection legal_knowledge --top-k 3

# 考卷命中率
python -c "from retrieve import evaluate_exam; print(evaluate_exam('考卷1.0.docx', \
    db_path='./legal_knowledge_db', collection_name='legal_knowledge', \
    top_k=5, tag_weight=0.25))"
```

> **建议把知识文件单独放一个 `knowledge/` 目录再导入**，不要 `--source .`，
> 否则容易把考卷文件一起导进知识库，命中率会被污染。

## 4. 第二层：AI 问答与管控

第一层把相关知识捞出来之后，这一层负责"**让 AI 说对话**"。

### 4.1 完整流水线

```
问题
 → case_guard.pins()      判断本题必须带哪些条文（不许漏）
 → kb.retrieve()          按相关度挑出 3 条知识
 → case_guard.directives() 拼出本题额外的强制指令
 → llm.ask()              约束 prompt + 调用大模型
 → citation_guard.check() 法条编号不在参考条文里 → 打回重写
 → case_guard.check_all() 该讲的要点没讲全 → 打回重写
 → output_guard           格式掰正、免责声明强制贴上
 → 回答
```

### 4.2 三道防线分别防什么

| 防线 | 文件 | 防的是 |
|---|---|---|
| 出处校验 | `citation_guard.py` | AI 编法条编号、把条文张冠李戴 |
| 硬规则验收 | `case_guard.py` | 该讲的例外没讲、法律适用判断错 |
| 格式强制 | `output_guard.py` | 免责声明漏了/写错了、中文问题用英文答 |

前两道防线不合格会**要求模型重写**，第三道防线直接由程序动手改。

### 4.3 场景识别

每个回答最前面会顶一行「本题属于哪个场景」：

```
【本题场景】知识库第9条 · 买方以"轻微瑕疵"拒收全部货物，合法吗？（实体救济）
【相关场景】知识库第1条 · 买方无正当理由拒收货物，卖方有哪些救济选择？（实体救济）
```

**这一行完全由程序算出来，不经过 AI。** 哪几条被检索命中本来就是程序自己挑的，
照实报一遍而已，因此不存在"编造场景"的可能。

场景口径来自法学组：**场景就是知识库这 20 条本身**，大类写在每条的【场景标签】里——
实体救济 10 条（第 1–10 条）／合同审查 6 条（第 11–16 条）／程序应急 4 条（第 17–20 条）。

### 4.4 检索打分（`kb.py`）

不做整段字符串比对，而是：中文切成两字一组，英文按词并去词尾，
再按 **TF-IDF** 加权——20 条里越少见的词越能说明问题（"停运"很值钱，"合同"几乎不加分）。
低于阈值就判定"超出知识库范围"，**宁可说不知道，也不硬凑一条不相关的**。

英文检索词单独维护在 `kb.py` 的 `EN_TERMS` 里，词源是法学组的《中英法律术语对照表》。
**刻意不写进 `kb_raw.txt`**——那是法学组的交付物，保持只读，她们下次更新可以直接覆盖。

### 4.5 合同初筛

读一份合同（.txt / .md / .docx），逐条比对法学组的 6 条审查规则，输出风险报告：

```
汇总：高风险 2 项 / 中风险 3 项 / 已覆盖 1 项
[高风险] 规则1 · 缺少卖方救济条款
   后果：...
   建议：...
   依据：...
```

**这个模块一行 AI 都不调**，纯关键词扫描。同一份合同扫一百遍结果完全一样，答辩时可当场演示。

## 5. 环境准备与快速开始

### 5.1 装依赖

```bash
python -m pip install -r requirements.txt
```

### 5.2 配置 API key

在项目根目录建 `.env`：

```
DEEPSEEK_API_KEY=你的key
```

> ⚠️ **`.env` 绝对不能提交到 GitHub**，`.gitignore` 已经挡住了。
> 传上去等于把钱包挂网上。

### 5.3 三条最常用的命令

```bash
# 1) 不花钱：看某个问题会命中哪几条知识、触发哪些硬规则
python -c "import bot; print(bot.explain('客户说沙发有划痕要拒付，合法吗？'))"

# 2) 花钱：真的调 AI 作答
python -c "import bot; print(bot.answer('客户说沙发有划痕要拒付，合法吗？'))"

# 3) 不花钱：扫一份合同
python contract_prescreen.py 样例合同_买方格式.txt
```

### 5.4 给界面同学的接口

界面只需要调一个函数：

```python
import bot
info = bot.answer_detailed("客户说沙发有划痕要拒付，合法吗？", contract_text=None)
```

返回的字典里有：

| 字段 | 内容 |
|---|---|
| `answer` | 最终回答正文（**不含**场景行，避免界面重复渲染） |
| `scene_header` | 排好版的场景行，直接贴在回答上方即可 |
| `scenes` | 结构化场景列表 `[{"no":9,"title":...,"scene":...}]`，排第一的是主场景 |
| `provisions` | 本次喂给 AI 的条文（含知识库编号），可做"参考依据"折叠面板 |
| `命中条目` | 命中的知识库编号列表 |
| `called_api` | 是否真的调用了大模型（超出知识库范围时为 `False`） |
| `trace` | 审核过程：程序打回并要求重写了几次、每次因为什么 |

`trace` 是答辩时的加分项——可以在界面上做一个「审核过程」折叠面板，
现场展示"程序拦下并要求重写 N 次"。

## 8. 已知边界（写清楚，免得被问住）

- **不是律师，也不打算是。** 系统只出初步风险提示，所有输出都带免责声明。
- **知识库只有 20 条。** 超出范围时程序会明确回答"超出知识库范围"，
  **不会**硬凑一条不相关的条文糊弄过去。
- **法条编号防得住，法条解释防不住。** `citation_guard` 能拦住编造的编号，
  但"编号对、解释错"目前只能靠约束 prompt，没有程序级的兜底。
- **中英术语对照表已接入检索，但知识库正文仍是中文。** 英文提问能检索到正确条目，
  回答质量取决于模型；条目标题暂不硬翻，等法学组出正式英译。
- **合同初筛只认关键词。** "合同里有没有写这块内容"判得准，
  "写得好不好"判不了——那需要条款文本级的语义比对。

## 9. 提交约定

**要提交的：** 源码、README、知识源文件（JSON / DOCX / TXT）、`requirements.txt`、`.gitignore`

**不提交的：**

```gitignore
.env
legal_knowledge_db/
*.sqlite3
__pycache__/
*.pyc
```

`legal_knowledge_db/` 是生成物不是源码，别人拉下来自己跑一次 `ingest.py` 就能重建，
提交它只会让仓库变大、版本管理变乱。`.env` 里是 API key，提交等于泄露。

直接推自己那份会把别人的内容覆盖掉——已经发生过一次了。

## 10. 常见问题

**Q：导入后检索不到内容？**
检查：是否执行过 `ingest.py`；数据文件是否被正确识别；
`category` 是否为 `实体救济` / `合同审查` / `程序应急` 三者之一；是否包含 `article` 和 `scenario`。

**Q：考卷命中率很低？**
可能是知识库没重建，或者 `--source .` 把考卷文件也导进去了，
或者切块粒度不合适。先把知识文件单独放一个目录再导。

**Q：能直接上传 Chroma 数据库吗？**
不建议。上传知识源，本地重新生成。

**Q：测试报 `No module named openai`？**
`PYTHONPATH` 没设成 `_stub`。Windows 用 `set PYTHONPATH=_stub`，Linux/Mac 用 `export`。

**Q：AI 回答里出现了知识库里没有的法条怎么办？**
不会出现——`citation_guard` 会拦下并要求重写。如果真的出现了，那是 bug，
请把问题原文和回答一起提 issue。
